Turn unanswered PR review feedback into verified fixes under the user's direction. Keep local completion separate from GitHub thread resolution.

## Steps

1. **Identify the PR and user.** Read the project's agent instructions. Use the supplied PR number or URL, otherwise the current branch's PR. Ask if the target remains ambiguous. Get the authenticated GitHub login; use it as the user unless the conversation identifies another login. Record the PR repository, head branch and SHA. Inspect the working tree before editing; preserve existing user changes and ensure fixes target the PR head.

2. **Collect unanswered threads.** Follow "Read review threads" in [references/gh-review.md](references/gh-review.md). Fetch every page of threads and every page of comments within each thread. Include a thread only when `isResolved` is false and none of its replies is authored by the user. Exclude threads started by the user. Keep outdated unresolved threads: inspect the current code before deciding whether their concern remains. Treat each thread as an issue, retaining its thread ID, root comment ID, URL, author, location and complete discussion. If a thread contains independent requests, give them separate issue IDs linked to the same thread; resolve that thread only when all its requests are addressed. PR conversation comments and review summaries lack this thread resolution state; state that the inventory covers inline review threads. No eligible threads: report that and stop. Incomplete or inaccessible discussion data: report the gap and complete discovery before presenting the inventory as exhaustive.

3. **Propose and wait.** Read the relevant code and show the complete numbered issue list before changing files. For each issue include its comment link, location, the concern, whether it still applies, a suggested resolution and the checks that would verify it. Include alternatives when there is a material tradeoff. Ask the user to choose for each ID: use the suggestion, provide another approach, skip, or discuss. Accept a batch answer or work through the list individually. An unanswered item stays pending; silence is not approval. Implement only issues with an explicit decision. Keep a ledger of decisions and outcomes so partial answers and later turns retain their scope.

4. **Delegate fixes, one sub-agent per issue.** For each approved code or documentation fix, launch a dedicated sub-agent with the issue ID, full discussion, chosen approach, relevant project instructions, PR head context, allowed scope and verification expectations. Each worker owns only that issue and returns its changes, checks and remaining concerns. Keep all GitHub replies and thread resolution in the parent session; workers must not post, resolve, commit or push. Run independent fixes concurrently only when their edits can coexist safely. Sequence issues with overlapping files or dependencies, giving later workers the integrated result. Preserve unrelated changes. If sub-agents are unavailable, report the limitation and ask how to proceed rather than silently replacing the requested delegation with parent-only fixes. A skip or explanation-only decision needs no fix worker.

5. **Integrate and verify.** Inspect every worker's result against the chosen resolution, integrate the fixes, and run the relevant combined checks. A worker's completion claim alone is insufficient. Keep failed or blocked issues open in the ledger and ask for the user's direction if the approved approach cannot complete them. Repeat the decision/fix loop until every issue is verified as addressed, already addressed with evidence, handled by an agreed explanation, or explicitly skipped. A blocked issue counts as skipped only when the user chooses that outcome. Record whether fixes exist locally or on the PR head.

6. **Finalise the branch.** Before preparing or posting PR replies, follow the [finalise skill](../../finalise/SKILL.md) on this PR's head branch. This workflow authorizes that hand-off, including finalise's commit and push steps for the approved work. Pass the merge-base of the PR's base branch and head as its fixed point so review covers the PR's changes even when the head tracks an already-pushed remote branch. Retain the existing PR, branch and base through its `git create-pr` hand-off. Keep review-thread replies and resolution deferred to the approval below. Finalise must complete, including its CI monitoring, before proceeding; report blockers and resume here once they are cleared. Refresh the issue ledger and verification evidence after any finalise fixes.

7. **Prepare replies and ask.** After finalise completes, show a per-thread proposal: the exact reply text, supporting changes and checks, whether the fix is local or pushed, and whether to resolve or leave open. For skipped issues default to no reply and leave open; an agreed explanation may justify a reply, but disagreement alone does not establish resolution. A thread is eligible for resolution only when every concern in it has been addressed and any required fix is present on the PR head. Ask whether to post the proposed comments and resolve the indicated threads, allowing approval for only selected actions. **Wait for the user's answer.** Earlier approval to implement fixes or finalise the branch does not authorize these GitHub actions. If approval is declined, leave the prepared replies available and finish with the branch results.

8. **Publish approved actions.** Re-fetch the affected threads and PR head before writing. If new feedback or head changes invalidate a proposal, return that item to the user; do not apply stale approval to changed content. Follow the shared reference to post approved replies, then resolve only the approved eligible threads. Check current replies and resolution state before retrying an uncertain request so a partial failure does not create duplicates. Report each issue's outcome, verification, whether its fix reached the PR, and which replies and resolutions actually succeeded. Keep skipped, unapproved and failed actions visible.
